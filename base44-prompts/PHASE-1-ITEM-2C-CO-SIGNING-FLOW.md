# Phase 1 Item 2c — Change Order signing flow (FSChangeOrder + FSProject schema)

> PRE-REQUISITE for community-node Phase 1 Item 2c (CO math + signing flow + total_budget recompute).
> Per DEC-093: please apply these schema changes in the Base44 dashboard before/with the matching code push.
> Per DEC-178: code-level schema changes ship paired with this prompt.
> **Please stay in discussion mode until every section below is confirmed (DEC-144).**

This prompt:
1. Adds 4 portal/signing fields to **FSChangeOrder** (mirrors fields already present on FSEstimate).
2. Relaxes **FSChangeOrder** Update permission so the new `signChangeOrder` server function can write via `asServiceRole` (mirrors the FSEstimate / FSDocument pattern from DEC-095).
3. Relaxes **FSProject** Update permission so the same server function can recompute `total_budget` after a CO is signed (mirrors same pattern).
4. Creates a new server function **`signChangeOrder`** that the unauthenticated client portal calls when the client signs a change order.

Nothing destructive. No fields renamed or removed. No existing records modified. The server function is purely additive.

---

## 1. FSChangeOrder — add 4 fields

Mirror what already exists on FSEstimate. These are the fields the client-portal signing flow needs.

| Field Name | Type | Required | Default | Description |
|---|---|---|---|---|
| portal_token | Text | No | — | Unique token for client signing/viewing link. Generated by the application when a CO is sent for signature. Validates the unauthenticated portal request server-side. |
| portal_link_active | Boolean | No | — | Whether the signing link is currently valid. Set to `true` when the CO is sent for signature, `false` when recalled or after signing completes. |
| sent_for_signature_at | Text (datetime ISO string) | No | — | ISO datetime when the CO was sent for signature. Set alongside `status: 'awaiting_signature'`. |
| recalled_at | Text (datetime ISO string) | No | — | ISO datetime when the CO was recalled (status returned from `awaiting_signature` to `draft`). |

Notes:
- These fields exist on FSEstimate already. The application code mirrors the FSEstimate signing flow exactly.
- All four fields are nullable. Existing CO records work unchanged.

## 2. FSChangeOrder — change Update permission

Currently the FSChangeOrder Update permission is **Creator Only** (`security.update.owner = true`).

Please change it to **No restrictions** (the same setting FSEstimate and FSDocument use today, per DEC-095).

The reason: the new `signChangeOrder` server function (Section 4 below) is called by an **unauthenticated** portal client. The function uses `asServiceRole` to update FSChangeOrder. Per DEC-095, `asServiceRole` does NOT bypass Creator Only update RLS in SDK 0.8.23, so the entity-level permission must be open and the security membrane moves to the function level (DEC-140 pattern).

Security is preserved by:
- The server function validates the `portal_token` matches the CO record before any update.
- The server function validates the CO is in a signable state (`awaiting_signature` or `sent`).
- Only the contractor who created the CO has the portal_token (it's surfaced via "Send for Signature" → clipboard → text to client).

---

## 3. FSProject — change Update permission

Currently the FSProject Update permission is **Creator Only** (`security.update.owner = true`).

Please change it to **No restrictions**.

The reason: when a CO is signed, the `signChangeOrder` server function (Section 4 below) recomputes `FSProject.total_budget` as `original_budget + sum(FSChangeOrder.amount where status = 'signed')`. The recompute runs in the server function via `asServiceRole`. Per DEC-095, this requires the entity-level permission to be open. Security is preserved at the function level — the only writer of `total_budget` is the system, triggered by a validated signing event.

`original_budget` remains immutable per DEC convention (FSProject schema description); only `total_budget` is touched by the recompute.

## 4. Create server function — `signChangeOrder`

Create a new server function called **`signChangeOrder`** (camelCase, exact spelling — the client code calls `invokeUnauthenticated('signChangeOrder', ...)`).

Mirrors the existing `signEstimate` function pattern. Code lives in `community-node/base44/functions/signChangeOrder/entry.ts` and will sync from GitHub on the next publish (per DEC-113).

Behavior:
1. Accept `{ change_order_id, portal_token, signature_data }` from the request body.
2. Validate all three are present.
3. Fetch the CO via `asServiceRole.entities.FSChangeOrder.get(change_order_id)`.
4. Verify `portal_token` matches the stored value.
5. Verify status is `'awaiting_signature'` or `'sent'`.
6. Verify `portal_link_active !== false`.
7. Update the CO: `status: 'signed'`, `signed_at: now`, `signature_data: JSON.stringify(...)` if needed, `portal_link_active: false`.
8. **Recompute parent project's `total_budget`:** fetch all signed COs for the same `project_id`, sum their `amount` field (fall back to `total` for legacy COs without `amount`), add to `original_budget`, write back to FSProject via `asServiceRole`.
9. Return `{ success: true }`.

The exact source code is in the GitHub repo at `base44/functions/signChangeOrder/entry.ts`. The Base44 publish step picks it up from there (DEC-113).
